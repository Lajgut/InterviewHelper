## В1 · Null-safety / smart cast — 🟡

**Спрошено было:** null-safety vs Java, что такое smart cast, и когда smart cast НЕ сработает даже после проверки.

**Твой ответ:** механизм типов страхует от NPE; nullable требует проверки (`!!` или убедиться в non-null); platform types из Java (`String!`) не контролируются — можно поймать NPE.

**✅ Верно:**
- Суть системы типов: проверка на компиляции vs падение в рантайме
- Nullable требует обработки
- **Platform types (`String!`) — отличная глубина!** Мало кто называет. Это подняло оценку

**❌ Ошибки и пробелы:**
- `!!` подан как основной инструмент — а он **небезопасный** (бросает NPE). Интервьюер съест: «твой главный инструмент от NPE — бросить NPE?»
- **Smart cast не раскрыт вообще** — а это была вторая половина вопроса

**📖 Эталон:**
> Null-safety — система типов: `String` не может быть null, `String?` — может. Обработка: `?.` (safe call), `?:` (Elvis), `x?.let { }`, `if (x != null)`. `!!` — только при 100% уверенности (code smell).
> **Smart cast**: после `if (x != null)` компилятор сам сужает `String?` → `String` внутри блока.
> **Smart cast НЕ работает, если:** ① `var`-свойство класса (другой поток изменит между проверкой и использованием), ② свойство с custom getter (нет backing field), ③ open-свойство (переопределят наследники), ④ локальная `var`, захваченная модифицирующей лямбдой.
> Лечение — локальная val-копия: `val v = field ?: return`.

**🎯 Подучить:** 4 случая отказа smart cast (списком!); повторить `?.`/`?:`/`let` как главные инструменты.

## В2 · Scope functions — 🔴 (слабейшая тема)

**Спрошено было:** `let/run/apply/also/with` — разница, use-cases, что возвращает context object vs lambda result.

**Твой ответ:** let/run возвращают объект (❌); разница — доступ через `it` или `this`; apply — действия и вернуть объект; «местами путаюсь».

**✅ Верно:**
- Ось `it` vs `this` — держится
- `apply` — настроить объект и вернуть его
- Честность о пробелах

**❌ Критичная ошибка:**
- **«let и run возвращают объект» — НЕВЕРНО.** Они возвращают **результат лямбды**. Объект возвращают только `apply` и `also`. Перепутана главная ось темы.

**📖 Эталон — таблица (зубрить):**

| Функция | Внутри | Возвращает | Use-case |
|---------|--------|-----------|----------|
| `let` | `it` | **результат лямбды** | `x?.let { }` — работа с nullable; маппинг |
| `run` | `this` | **результат лямбды** | `val area = rect.run { w * h }` |
| `with` | `this` | результат лямбды | групповые операции; **НЕ extension** |
| `apply` | `this` | **ОБЪЕКТ** | конфигурация: `Intent().apply { putExtra() }` |
| `also` | `it` | **ОБЪЕКТ** | side-effect в цепочке: `.also { log(it) }` |

**Мнемоники:** «**A** = объект вернётся» (Apply, Also). `also` = «также» = сделать дополнительно и вернуть как был. `this` = объект «стал тобой»; `it` = объект «рядом».

**🎯 Подучить:** таблицу целиком + мнемонику. Это чистая зубрёжка — 15 минут закрывает навсегда.

## В3 · inline / noinline / crossinline / reified — 🟡

**Спрошено было:** что даёт `inline`, почему возможен `reified`, когда нужен `crossinline`.

**Твой ответ:** встраивает код вместо лямбды → нет объекта → лучше по производительности; главный смысл — non-local returns; `reified` в связке с inline узнаёт тип; `crossinline` = «вставка разрешена, non-local return запрещён».

**✅ Верно:**
- Механика встраивания + отсутствие аллокаций
- **Non-local returns как мотивация** — продвинутый нюанс
- `crossinline` — точное определение одной фразой
- `reified` связан с `inline`

**❌ Пробелы:**
- **Не объяснил, ПОЧЕМУ `reified` требует `inline`** (механика type erasure) — а это была суть вопроса
- Нет примеров (`filterIsInstance<T>`, `startActivity<T>`)
- `noinline` не затронут
- Фраза про «переиспользование объекта» перевёрнута: при частых вызовах inline **раздувает байткод** (code bloat)

**📖 Эталон:**
> Без inline работает **type erasure**: `fun <T> typeName() = T::class.java` — не скомпилируется, T стёрт в рантайме.
> С `inline + reified` тело копируется **в точку вызова**, где компилятор знает конкретный тип. Фраза-ответ: *«reified существует, потому что после встраивания стирается не тип, а граница функции»*.
> `noinline` — оставить лямбду объектом (сохранить в поле, передать).
> `crossinline` — лямбда уезжает в другой контекст (`Handler.post { action() }`): non-local return физически бессмыслен, компилятор требует явного согласия.

**🎯 Подучить:** фразу про reified + type erasure; noinline-кейс «сохранить лямбду»; задачу «напиши postDelayed» (упирается в crossinline).

## В4 · Variance (in/out) — 🔴

**Спрошено было:** что значат `out T`/`in T`, примеры из stdlib, star-projection, подвох с массивами Java.

**Твой ответ:** это ковариантность/контравариантность, аналог wildcards Java; «не помню, что in, что out»; Float/Integer — потомки Number; `List<*>` — «тип известен в рантайме, можно cast»; про массивы — не знаю.

**✅ Верно:**
- Термины знаешь
- Связь с Java wildcards
- Иерархию типов понимаешь (Number)

**❌ Критично:**
- **Ядро (что есть `in`, что `out`) — не знает.** Тема не отвечает
- **Star-projection объяснён неверно**: «тип известен в рантайме, cast» — это описание **type erasure** (другая тема!). `List<*>` — «тип неизвестен, компилятор разрешает только безопасные операции»
- Примеры stdlib не названы
- Массивы Java — пропуск

**📖 Эталон:**
> **out = output/producer** — класс только ОТДАЁТ T: `List<out E>` (читаем).
> **in = input/consumer** — класс только ПРИНИМАЕТ T: `Comparable<in T>` (передаём).
> Мнемоника: **out = output, in = input**. Java-PECS: Producer Extends, Consumer Super.
> `List<out Cat>` можно использовать как `List<Animal>` ✅ — читаем же, подменить нельзя.
> `Comparable<in Animal>` можно как `Comparable<Cat>` ✅ — кот точно животное.
> **`List<*>`** — «один конкретный тип, который я не знаю»: читать как `Any?` ✅, добавлять ❌.
> **`List<Any?>`** — «элементы любые вперемешку»: добавлять ✅.
> Java-массивы ковариантны → `Object[] o = new String[1]; o[0] = 42;` → **ArrayStoreException** в рантайме. Kotlin `Array<T>` инвариантен — дыры нет.

**🎯 Подучить:** мнемонику out/in; пару `List<*>` vs `List<Any?>` (классический подвох); `List<out E>` + `Comparable<in T>` как stdlib-примеры.

## В5 · Делегаты (lazy / lateinit) — 🟡

**Спрошено было:** `by lazy` под капот + режимы синхронизации; `lazy` vs `lateinit`; эксепшн и безопасная проверка; другие делегаты.

**Твой ответ:** lazy создаёт объект при первом обращении, «синглтон под капотом»; режимы не знаю; lateinit — контракт «инициализирую позже», при раннем обращении — ошибка; эксепшен «notInitializedException или типа того»; «можно try-catch»; «lateinit — моветон»; про observable/vetoable не сказал; свой делегат писал, но не помню.

**✅ Верно:**
- `Lazy<T>` + кеширование после первого обращения
- **Ключевое различие:** lazy создаст сам, lateinit упадёт — сформулировал точно
- `by remember`, `by viewModels` всплыли из практики — живой стек

**❌ Ошибки:**
- **try-catch — антипаттерн.** Есть `::prop.isInitialized`
- «lateinit — моветон» — **нет**: стандарт DI (`@Inject lateinit var`), тесты (`@Before`). Моветон — только когда есть альтернатива
- Эксепшен: `UninitializedPropertyAccessException` (был рядом)

**❌ Пробелы:**
- Режимы `LazyThreadSafetyMode` — не знал
- Ограничения lateinit (только `var`, non-null, не примитивы)
- `Delegates.observable` / `vetoable`

**📖 Эталон:**
```kotlin
val a by lazy { ... }                    // SYNCHRONIZED (default): double-checked locking
val b by lazy(PUBLICATION) { ... }       // гонка потоков, победитель кешируется
val c by lazy(NONE) { ... }              // без замков — main-thread сценарий

@Inject lateinit var api: Api            // DI-кейс — легитимно
if (::api.isInitialized) ...             // ✅ безопасная проверка

var name by Delegates.observable("") { _, old, new -> }  // слушатель
var age by Delegates.vetoable(0) { _, _, new -> new >= 0 } // запрет значения

class D : ReadWriteProperty<Any?, String> {              // свой делегат:
    override fun getValue(r: Any?, p: KProperty<*>) = ...
    override fun setValue(r: Any?, p: KProperty<*>, v: String) { ... }
}
```

**🎯 Подучить:** 3 режима lazy (+ мнемоника: очередь / гонка / без замков); `isInitialized`; observable/vetoable в двух словах.

## В6 · data / sealed / companion — 🟡

**Спрошено было:** методы data class; контракт equals/hashCode; copy; sealed vs enum + ограничение; companion.

**Твой ответ:** data class генерирует hashCode, equals, toString (неполный список); equals — по данным, hashCode — для бакетов хэш-таблиц; copy — другой объект с теми же полями, удобно менять 1–2 поля; sealed — enum на уровне классов, безопасность when, «если это единственная причина — лучше enum»; object — статик-класс; companion — доступ без экземпляра, «про не-static не знаю».

**✅ Верно:**
- 3 из 5 генерируемых методов
- **Механика бакетов** — суть подвоха ухвачена
- `copy` — польза при большом числе полей
- **sealed vs enum — зрелое рассуждение** (даже про время компиляции)
- `object` как singleton

**❌ Пробелы:**
- **`componentN()` не назван** (деструктуризация `val (a, b) = pair`) — спрашивают полным списком
- **Контракт не сформулирован словами:** «равные → равные hashCode, обратное — нет»
- **Ограничение sealed не названо:** все наследники — в том же модуле
- `copy` + `apply` — работает, но идиоматичнее `obj.copy(name = "x")`; главный Android-кейс — **иммутабельные state-обновления в MVI**
- Companion-механика — не знал

**📖 Эталон (companion — главная добивка):**
> `companion object` — **реальный объект-синглтон** внутри класса (с именем `Companion`). Как объект он умеет то, что Java-static не умеет: реализовывать интерфейсы (Factory), расширяться extension-функциями, передаваться как значение. Java видит `User.Companion` → для настоящего static есть `@JvmStatic`.
```kotlin
class User private constructor(val name: String) {
    companion object Factory : NameProvider { fun create(n: String) = User(n) }
}
fun User.Factory.fromJson(s: String) = ...    // extension на companion
val f: NameProvider = User                     // companion передаётся!
```

**🎯 Подучить:** полный список data-class методов (5 шт.); контракт equals/hashCode одной фразой; sealed-ограничение (модуль); companion-фокус.

## В7 · Коллекции vs Sequence — 🟡

**Спрошено было:** механика выполнения (сколько проходов, когда обрабатываются элементы); когда выигрыш/проигрыш; что такое ленивость; sequence builder.

**Твой ответ:** каждая операция на List создаёт новую коллекцию (3 оператора = 3 коллекции); Sequence — без промежуточных сущностей; «что за сущность — объяснить не могу»; «выигрывает при 2+ операторах»; «без toList() останется последовательностью».

**✅ Верно:**
- Суть выигрыша — промежуточные аллокации
- «1 оператор — смысла нет»
- Честные границы знания

**❌ Пробелы:**
- **Механика не раскрыта** — а это был главный вопрос: eager «горизонтально» (операция за операцией, каждая по ВСЕЙ коллекции) vs lazy «вертикально» (один элемент сквозь весь пайплайн)
- **Ранний выход** (`first()` не трогает хвост) — не назван, а это главный выигрыш
- «Без toList() останется последовательностью» — слабо: **не выполнится НИ ОДИН элемент**
- Терминология: «терминальный создаёт коллекцию» — наоборот, **промежуточные** на List аллоцируют

**📖 Эталон — картинка:**
```kotlin
list.map { it * 2 }.filter { it > 2 }.first()
// EAGER: map все 3 → [2,4,6]; filter все 3 → [4,6]; first → 4
//   = 6 вычислений, 2 списка

list.asSequence().map { it * 2 }.filter { it > 2 }.first()
// LAZY: elem1 → map→2 → filter fail; elem2 → map→4 → filter ok → first=4. СТОП
//   = 2 вычисления, 0 списков, elem3 НЕ ТРОНУТ
```
> Ленивость одной фразой: *«промежуточные операции ничего не вычисляют — строят конвейер; терминальная запускает обработку по одному элементу за раз»*.
> Когда Sequence: ранний выход / 1000+ элементов / длинные цепочки. Когда нет: маленькие списки, простые операции (оверхед пайплайна).
> Builder: `generateSequence(0 to 1) { (a, b) -> b to a + b }` — бесконечные последовательности.

**🎯 Подучить:** механику element-by-element; правило «ранний выход + 1000+»; фразу про «ни одного элемента без терминальной».

## В8 · `==` / `===` / equals — 🟡 (лучший ответ секции)

**Спрошено было:** что делают `==`/`===`; почему `==` не падает на null; Integer cache; строки.

**Твой ответ:** `==` это equals, `===` — ссылки; «null — тоже тип, Int? == Int будет false»; a==b true, c==d false «кэш интов, 8-битный, -128..127»; «Kotlin сравнит содержимое, Java — ссылки».

**✅ Верно:**
- п.1 — точно
- **п.3 — ИДЕАЛЬНО: Integer cache с диапазоном!** Самый коварный подвопрос закрыт. Редкость
- п.4 — суть верна

**❌ Пробел:**
- п.2: вопрос «почему не падает» — отвечен фактом вместо механики. Интервьюер ждал **формулу компиляции**

**📖 Эталон:**
```kotlin
a == b   →   a?.equals(b) ?: (b === null)
```
> Если `a != null` → equals; если `a == null` → equals **не вызывается**, идёт `b === null`. Вот весь секрет null-безопасности. Бонус: `null == null` — `true`.
> Строки: литерал из **string pool**, `new String("s")` — новый объект → в Java `==` даёт false; Kotlin `==` уходит в equals → true.

**🎯 Подучить:** формулу `a?.equals(b) ?: (b === null)` — она же ответ на null-вопрос.

## В9 · Исключения / Result / runCatching — 🔴 (важнейшая для практики)

**Спрошено было:** checked в Kotlin и `@Throws`; операции Result; что ловит runCatching; разбор кода.

**Твой ответ:** в Kotlin всё компилируется без обработки checked (верно); «@Throws не даёт компилить или предупреждает — не помню»; Result — «удобный синтаксис, у нас в компании под запретом, интересно почему»; **«runCatching ловит всё, КРОМЕ CancellationException»**; задачу с кодом — «не знаю».

**✅ Верно:**
- «В Kotlin все исключения unchecked»
- **Инсайт «Result под запретом в компании»** — правильная практика, теперь знаешь почему

**❌ Критичные ошибки:**
- **п.3 ИНВЕРТИРОВАН:** runCatching ловит **ВСЁ (`Throwable`), ВКЛЮЧАЯ CancellationException** — и это его главная опасность. Ты сказал наоборот
- `@Throws`: не влияет на компиляцию Kotlin — он **только для Java-интеропа** (пишет `throws` в байткод)
- Операции Result (`fold`, `onSuccess`…) не названы
- Код-ревью задача не решена

**📖 Эталон:**
```kotlin
inline fun <R> runCatching(block: () -> R): Result<R> =
    try { Result.success(block()) }
    catch (e: Throwable) { Result.failure(e) }   // ← ВСЁ, включая Cancellation и Errors
```
> **Почему запрещают Result в компаниях:** ① компилятор запрещает `Result` как return type функции; ② легко проглотить failure; ③ runCatching в suspend ловит CancellationException → **ломает отмену корутин** (официальная позиция kotlinx: не использовать в suspend).

```kotlin
// ПЛОХО (твой вопрос 4): поймает Cancellation (сломал отмену) + NPE-баг замажет кэшем
val user = runCatching { api.getUser() }.getOrElse { cachedUser }

// ХОРОШО: конкретные типы + отмена наверх
val user = try {
    api.getUser()
} catch (e: CancellationException) { throw e }   // ВСЕГДА rethrow
catch (e: IOException) { cachedUser }
```

**🎯 Подучить:** правило «runCatching = catch(Throwable) → CancellationException rethrow»; лови конкретные типы. **Это мост в секцию Coroutines — там всплывёт обязательно.**
